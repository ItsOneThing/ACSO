Lezione 3

Programmazione concorrente

Cap. P3 delle dispense Pelagatti — perché i programmi multi-thread possono dare risultati sbagliati e come si rimedia con mutex e semafori.

1. Il modello di programmazione concorrente

Modello sequenziale

  • Istruzioni eseguite in un ordine prevedibile, che dipende dal codice e dai dati in ingresso.

Modello concorrente / parallelo

  • Più flussi di controllo in parallelo che interferiscono (condividono risorse, es. le stesse strutture dati).
  • Ordine di esecuzione non deterministico.
  • Il risultato dipende dai dati e dall'ordine di esecuzione → può influire sulla correttezza.
  • Le tecniche valgono per processi e thread, ma si usano soprattutto con i thread, che sono fortemente cooperanti perché condividono lo spazio di indirizzamento (tranne la pila).
  • Un programma multi-thread è potenzialmente non deterministico anche a parità di input: non si può prevedere la prossima istruzione eseguita e possono comparire errori dovuti proprio alla concorrenza.
Notazione Date due attività Ai e Bj, scriviamo Ai < Bj per "Ai avviene prima di Bj".
Sequenziali: vale sempre Ai < Bj, oppure sempre Bj < Ai.
Concorrenti: a volte Ai < Bj, a volte Bj < Ai (non determinismo temporale).
ti.j = istruzione j eseguita dal thread i.

2. Esempio 1: due thread che stampano

void *tf1(void *arg) { printf("x"); printf("y"); printf("z"); return NULL; }
void *tf2(void *arg) { printf("a"); printf("b"); printf("c"); return NULL; }

int main(void) {
   pthread_t tID1, tID2;
   pthread_create(&tID1, NULL, tf1, NULL);
   pthread_create(&tID2, NULL, tf2, NULL);
   pthread_join(tID1, NULL);
   pthread_join(tID2, NULL);
   printf("\nfine\n");
   return 0;
}

Ogni thread è sequenziale al suo interno, ma i due thread sono in concorrenza tra loro. Le stampe si possono mescolare (es. xaybzc, abxcyz, xyzabc…), però viene sempre rispettato l'ordinamento parziale:

x < y < z        a < b < c

fine viene sempre stampato per ultimo, perché main fa prima le due join.

3. Correttezza di un programma concorrente

  • Dimostrazione formale (logica formale): molto difficile.
  • Testing (provo input e controllo output): funziona bene per programmi sequenziali, ma in quelli concorrenti l'output dipende anche dall'ordine di esecuzione, che cambia da un'esecuzione all'altra. Un test che passa 1000 volte non garantisce che passi la 1001ª.

Servono quindi costrutti di programmazione appositi per affrontare tre problemi:

  1. Sequenze critiche e mutua esclusione (mutex)
  2. Deadlock
  3. Sincronizzazione (semafori)

4. Sequenza critica e mutua esclusione

Sequenza critica Sequenza di istruzioni eseguita da thread paralleli che non deve essere "mescolata" con le istruzioni degli altri thread, altrimenti il risultato può essere sbagliato.

Bisogna sequenzializzare la sequenza critica tra i thread: se un thread inizia la sequenza critica, deve eseguirla tutta prima che un qualunque altro thread possa iniziarla. (Si riduce la concorrenza, ma si guadagna correttezza.)

Mutua esclusione La proprietà che vogliamo garantire sulle sequenze critiche: al massimo un thread alla volta le sta eseguendo.

Se nell'esempio 1 le tre printf di ciascun thread formano una sequenza critica, gli unici output ammessi sono:

xyzabc        oppure        abcxyz
fine                        fine

5. Esempio 2: trasferimento tra conti correnti

Due conti, contoA e contoB (variabili globali). La funzione trasferisci() preleva un importo da B e lo deposita su A. La somma dei due conti deve restare invariata: è l'invariante della funzione.

int contoA = 100, contoB = 200;
int totale;

void *trasferisci(void *arg) {
   int importo = * ((int *) arg);
   int cA, cB;
   // inizio sequenza critica
   cA = contoA;              // 1. leggi contoA in var. locale
   cB = contoB;              // 2. leggi contoB in var. locale
   contoA = cA + importo;    // 3. aggiorna contoA
   contoB = cB - importo;    // 4. aggiorna contoB
   // fine sequenza critica
   return NULL;
}

int main(void) {
   pthread_t tID1, tID2;
   int importo1 = 10, importo2 = 20;
   pthread_create(&tID1, NULL, trasferisci, &importo1);
   pthread_create(&tID2, NULL, trasferisci, &importo2);
   pthread_join(tID1, NULL);
   pthread_join(tID2, NULL);
   totale = contoA + contoB;
   printf("contoA = %d contoB = %d\n", contoA, contoB);
   printf("il totale è %d\n", totale);
   return 0;
}

Valori iniziali A = 100, B = 200. t1 trasferisce 10, t2 trasferisce 20. Risultato corretto atteso: A = 130, B = 170, totale 300.

Alcune possibili sequenze:

  • S1 t1.1 < t1.2 < t1.3 < t1.4 < t2.1 < t2.2 < t2.3 < t2.4 → corretta
  • S2 t2.1 … t2.4 < t1.1 … t1.4 → corretta
  • S3 t1.1 < t1.2 < t1.3 < t2.1 < t2.2 < t2.3 < t2.4 < t1.4 → sbagliata:
dopoiniziot1.1t1.2t1.3t2.1t2.2t2.3t2.4t1.4
contoA100110130
contoB200180190
cA (t1)100
cB (t1)200
cA (t2)110
cB (t2)200
Cosa è andato storto t2 legge contoB (= 200) prima che t1 lo abbia aggiornato. Alla fine t1 scrive contoB = 200 − 10 = 190, sovrascrivendo l'aggiornamento di t2. Risultato: A = 130, B = 190, totale 320 → sono "comparsi" 20 euro. L'invariante è violato.

Questo tipo di errore si chiama in generale race condition: il risultato dipende da chi "vince la corsa".

6. Istruzioni atomiche

Supponiamo di riscrivere il trasferimento con due sole istruzioni:

a.  contoA = contoA + importo;
b.  contoB = contoB - importo;

Se ciascuna di a e b fosse atomica (indivisibile), qualsiasi intreccio dei due thread darebbe il risultato corretto, non solo quelli ovvi (t1.a < t1.b < t2.a < t2.b) ma anche ad esempio t1.a < t2.a < t1.b < t2.b o t1.a < t2.a < t2.b < t1.b: somme e sottrazioni commutano, quindi alla fine A = 130 e B = 170.

Ma le istruzioni di alto livello non sono atomiche

  • Il compilatore traduce ogni istruzione C in una sequenza di istruzioni macchina.
  • Sono atomiche solo le singole istruzioni in linguaggio macchina, non quelle di alto livello.
  • Il programmatore dovrebbe quindi sapere come il C viene tradotto.

contoA = contoA + 100 può diventare:

Processore che opera in memoria (es. Intel)

ADD contoA, 100   // 1 istruzione: atomica

Processore load/store (es. RISC-V)

ld   t0, contoA     // carica in t0
addi t0, t0, 100    // somma
sd   t0, contoA     // salva
Tre istruzioni: un altro thread può intervenire in mezzo → non atomica.

Lo stesso vale per il conta++ su variabile globale della Lezione 2.

7. Soluzione: la mutua esclusione con il mutex

Per garantire la correttezza di sequenze critiche (o istruzioni non atomiche) serve la mutua esclusione. In pthread il costrutto è il mutex:

  • è come un lucchetto che racchiude la sequenza critica, con un segnale di "occupato";
  • lock: un thread chiude il lucchetto ed entra; gli altri thread che provano a entrare restano in attesa;
  • unlock: il thread rilascia il lucchetto e uno di quelli in attesa può entrare.
PassoCodice
Dichiararepthread_mutex_t mx; (globale, così la vedono tutti i thread)
Inizializzarepthread_mutex_init(&mx, NULL);
Entrarepthread_mutex_lock(&mx);
Uscirepthread_mutex_unlock(&mx);

Esempio 1 con mutex

pthread_mutex_t mx;

void *tf1(void *arg) {
   pthread_mutex_lock(&mx);
   printf("x"); printf("y"); printf("z");
   pthread_mutex_unlock(&mx);
   return NULL;
}
void *tf2(void *arg) {
   pthread_mutex_lock(&mx);
   printf("a"); printf("b"); printf("c");
   pthread_mutex_unlock(&mx);
   return NULL;
}
// nel main, prima di creare i thread:
pthread_mutex_init(&mx, NULL);

Output: solo xyzabc oppure abcxyz.

Esempio 2 (conti) con mutex

pthread_mutex_t conti;

void *trasferisci(void *arg) {
   int importo = * ((int *) arg);
   int cA, cB;
   pthread_mutex_lock(&conti);
   cA = contoA;
   cB = contoB;
   contoA = cA + importo;
   contoB = cB - importo;
   pthread_mutex_unlock(&conti);
   return NULL;
}

Ora un thread non può leggere i conti mentre l'altro li sta aggiornando: il risultato è sempre A = 130, B = 170, totale 300.

Schema generale 
pthread_mutex_lock(&m);
   /* sequenza critica: accesso ai dati condivisi */
pthread_mutex_unlock(&m);
Con due thread che stampano "entro / termino seq critica", le due righe di un thread compaiono sempre consecutive.

8. Deadlock e mutex

Deadlock (attesa circolare) Si verifica quando due thread devono bloccare due risorse A e B (con due mutex diversi) ma le bloccano in ordine inverso:
  • thread_1 ha bloccato A e aspetta B;
  • thread_2 ha bloccato B e aspetta A.
Nessuno dei due può proseguire: il programma resta bloccato per sempre e va terminato dall'esterno.

Grafo di accesso alle risorse

Il deadlock corrisponde a un ciclo nel grafo di accesso alle risorse:

  • nodi = thread e risorse;
  • arco thread → risorsa: il thread è in attesa di bloccare la risorsa;
  • arco risorsa → thread: la risorsa è bloccata da quel thread.

Esempio

pthread_mutex_t mutexA, mutexB;

void *lockApoiB(void *arg) {
 4.  pthread_mutex_lock(&mutexA);
 5.  printf("thread%d: iniz1\n", (int) arg);
 6.  pthread_mutex_lock(&mutexB);
 7.  printf("thread%d: iniz2\n", (int) arg);
 8.  printf("thread%d: fine 2\n", (int) arg);
 9.  pthread_mutex_unlock(&mutexB);
10.  printf("thread%d: fine 1\n", (int) arg);
11.  pthread_mutex_unlock(&mutexA);
     return NULL;
}
void *lockBpoiA(void *arg) {
15.  pthread_mutex_lock(&mutexB);
16.  printf("thread%d: iniz2\n", (int) arg);
17.  pthread_mutex_lock(&mutexA);
18.  printf("thread%d: iniz1\n", (int) arg);
19.  printf("thread%d: fine 1\n", (int) arg);
20.  pthread_mutex_unlock(&mutexA);
21.  printf("thread%d: fine 2\n", (int) arg);
22.  pthread_mutex_unlock(&mutexB);
     return NULL;
}
// main: init dei due mutex, t1 esegue lockApoiB, t2 esegue lockBpoiA, poi join

Il main crea t1 (che esegue lockApoiB) e t2 (che esegue lockBpoiA): due sequenze critiche annidate in ordine inverso.

SequenzaCosa succede
t1.4 < t1.6 < t1.9 < t1.11 < t2.15 < t2.17 < t2.20 < t2.22OK: t1 blocca entrambi i mutex prima che t2 inizi (o viceversa)
t1.4 < t2.15 < t1.6 < t2.17Deadlock: t1 ha A, t2 ha B; t1 si blocca su B, t2 si blocca su A
t2.15 < t1.4 < t2.17 < t1.6Deadlock: stessa situazione, a ordine invertito
Come evitarlo (regola pratica) Far acquisire i mutex a tutti i thread nello stesso ordine (es. sempre prima A poi B): così il ciclo nel grafo non può formarsi.

9. Sincronizzazione e semafori

Sincronizzazione Una relazione temporale deterministica che si vuole imporre tra due o più thread (es. "B avviene sempre dopo A").

Il costrutto è il semaforo (<semaphore.h>):

  • variabile di tipo sem_t;
  • inizializzato con sem_init(&sem1, 0, valore_iniziale): il secondo parametro per noi è sempre 0, il terzo è il valore iniziale;
  • si comporta come un intero ≥ 0.
OperazioneSe valore == 0Se valore > 0
sem_wait(&s)il thread si blocca finché un altro thread non fa sem_postdecrementa e prosegue
sem_post(&s)incrementa il valore e prosegue; se c'era un thread bloccato in sem_wait, eventualmente lo sblocca

Interpretazione: "numero di risorse disponibili"

  • valore > 0 = quante risorse sono libere, cioè quanti thread possono fare sem_wait senza bloccarsi;
  • valore = 0 = nessuna risorsa libera, possono esserci thread in attesa;
  • sem_post = restituire una risorsa.
Semaforo come mutex Un semaforo inizializzato a 1 funziona come un mutex: sem_wait per entrare nella sequenza critica (la segna occupata), sem_post per uscire (sblocca chi aspetta o riporta il valore a 1).

10. Esempio: stampare esattamente "axbycz"

tf1 stampa x, y, z; tf2 stampa a, b, c. Vogliamo forzare l'alternanza axbycz. Servono due semafori, entrambi inizializzati a 0:

  • sem1 blocca il thread che stampa x, y, z;
  • sem2 blocca il thread che stampa a, b, c.
#include <semaphore.h>
sem_t sem1, sem2;

void *tf1(void *arg) {
   sem_wait(&sem1);                     // aspetto la 'a'
   printf("x");
   sem_post(&sem2); sem_wait(&sem1);    // passo il turno, aspetto la 'b'
   printf("y");
   sem_post(&sem2); sem_wait(&sem1);
   printf("z");
   return NULL;
}
void *tf2(void *arg) {
   printf("a");                         // parte subito
   sem_post(&sem1); sem_wait(&sem2);    // sblocco tf1, aspetto la 'x'
   printf("b");
   sem_post(&sem1); sem_wait(&sem2);
   printf("c");
   sem_post(&sem1);
   return NULL;
}
// nel main:
sem_init(&sem1, 0, 0);
sem_init(&sem2, 0, 0);

Come funziona:

  1. tf1 fa subito sem_wait(&sem1): sem1 = 0 → si blocca.
  2. tf2 stampa a, fa sem_post(&sem1) (sblocca tf1), poi sem_wait(&sem2) → si blocca.
  3. L'unico che può andare avanti è tf1: stampa x, sem_post(&sem2) sblocca tf2, sem_wait(&sem1) lo blocca.
  4. …e così via a turno: a x b y c z.

Le due funzioni sono asimmetriche perché si deve sempre cominciare con la "a".

11. Esempio: produttore / consumatore

Caso classico: un buffer condiviso, un thread produttore che ci scrive caratteri e un thread consumatore che li legge. Versione semplice: il buffer contiene un solo carattere.

Servono due semafori che descrivono lo stato del buffer:

SemaforoValore inizialeChi bloccaSignificato
pieno0il consumatorenumero di caratteri pronti da leggere (all'inizio nessuno)
vuoto1il produttorenumero di posti liberi nel buffer (all'inizio uno)
char buffer;
int fine = 0;
sem_t pieno, vuoto;

void *scrivi(void *arg) {          // PRODUTTORE
 5.  for (int i = 0; i < 5; i++) {
 6.     sem_wait(&vuoto);              // aspetto che il buffer sia libero
 7.     buffer = 'a' + i;
 8.     sem_post(&pieno);              // segnalo: c'è un carattere
     }
10.  fine = 1;
     return NULL;
}
void *leggi(void *arg) {           // CONSUMATORE
     char miobuffer;
16.  while (fine == 0) {
17.     sem_wait(&pieno);              // aspetto un carattere
18.     miobuffer = buffer;
19.     sem_post(&vuoto);              // libero il buffer
20.     printf("buffer contiene %.1s\n", &miobuffer);
     }
     return NULL;
}
// main: sem_init(&pieno, 0, 0); sem_init(&vuoto, 0, 1);  → buffer vuoto all'inizio

All'inizio il buffer è vuoto: parte il produttore, decrementa vuoto, scrive 'a', fa post su pieno sbloccando il consumatore, e così via. I caratteri prodotti sono a, b, c, d, e.

Errore: l'ultimo carattere può andare perso Il produttore scrive 'e' (t1.7), fa post (t1.8), esce dal for e pone fine = 1 (t1.10). Se t1.10 < t2.16, cioè fine diventa 1 prima che il consumatore ricontrolli la condizione del while, il consumatore esce dal ciclo e 'e' non viene mai letta.

Versione corretta

void *scrivi(void *arg) {
   for (int i = 0; i < 5; i++) {
      sem_wait(&vuoto);
      buffer = 'a' + i;
      if (i == 4) fine = 1;           // segnalo la fine PRIMA della post
      sem_post(&pieno);
   }
   return NULL;
}
void *leggi(void *arg) {
   char miobuffer; int i;
   while (fine == 0) {
      sem_wait(&pieno);
      miobuffer = buffer;
      sem_post(&vuoto);
      printf("buffer contiene %.1s\n", &miobuffer);
   }
   sem_getvalue(&pieno, &i);           // controllo per l'ultimo carattere
   if (i == 1) {                      // c'è ancora un carattere non letto
      miobuffer = buffer;
      printf("buffer contiene %.1s\n", &miobuffer);
   }
   return NULL;
}

Se il consumatore salta il ciclo che avrebbe letto 'e' (fine = 1 prima del suo controllo del while), dopo il while vede con sem_getvalue che pieno vale 1, cioè c'è ancora un carattere da consumare, e rifà l'ultima lettura.

Nota (mia, non nelle slide) Anche la versione corretta ha un caso limite: se il consumatore controlla il while dopo fine = 1 ma prima della sem_post(&pieno) finale, sem_getvalue trova ancora 0 e la 'e' si perde. Una soluzione più robusta è far contare al consumatore i caratteri letti (es. for (i = 0; i < 5; i++)) invece di usare la variabile fine.

Riassunto

  • Concorrenza → ordine non deterministico → il risultato può cambiare da un'esecuzione all'altra; il testing non basta.
  • Sequenza critica: codice che accede a dati condivisi e non va intrecciato con altri thread. Serve mutua esclusione.
  • Le istruzioni C non sono atomiche (es. x = x + 1 → load / add / store).
  • Mutex: pthread_mutex_init, lock, unlock; un thread alla volta nella sezione critica.
  • Deadlock: due thread che prendono due mutex in ordine inverso → ciclo nel grafo delle risorse. Evitarlo prendendo i lock sempre nello stesso ordine.
  • Semaforo: intero ≥ 0; sem_wait decrementa o blocca, sem_post incrementa e sblocca. Inizializzato a 1 = mutex; a 0 = "aspetta un segnale".
  • Esempi tipici: alternanza forzata (axbycz) e produttore/consumatore con semafori pieno (0) e vuoto (1).
