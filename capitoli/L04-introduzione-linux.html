Lezione 4

Introduzione a Linux

Cap. N1 delle dispense Pelagatti — a cosa serve il sistema operativo, come è organizzato Linux e quali strutture dati usa per rappresentare i processi.

SettoreSituazione

2. Evoluzione di Linux

  • Il codice di Linux cresce in modo quasi esponenziale, soprattutto per il supporto a sempre nuove periferiche: i gestori di periferica (driver) sono più del 50% del codice.
  • Versioni 4.x rilasciate nel 2015 (4.0 ad aprile, 4.4 a dicembre).
  • Dalla 2.0 alla 2.6 la complessità è aumentata per:
    • il passaggio da strutture statiche (array) a strutture dinamiche → niente più limiti rigidi sulle dimensioni, sistema più adattabile;
    • il supporto alle architetture multiprocessore, con molti problemi di sincronizzazione (vedi L03).
  • Dalla 2.6: interfaccia astratta del frame buffer della scheda grafica → le applicazioni grafiche possono accedervi senza conoscere i dettagli dell'hardware.

3. Funzioni principali del sistema operativo

Linux realizza l'ambiente di esecuzione dei programmi, fatto da un insieme di processi, in modo che:

  • ogni processo esegua il suo programma sequenzialmente;
  • processi diversi procedano "in parallelo";
  • un processo non possa disturbare gli altri (isolamento);
  • le risorse condivise (es. periferiche) siano gestite centralmente: un processo non vi accede direttamente ma chiede un servizio al SO, e il SO offre un modello semplice delle risorse (es. le periferiche viste come file speciali);
  • le periferiche siano gestite in modo efficiente (tenute attive il più possibile).

Come realizza il parallelismo: time-sharing

  • Linux è un SO multi-programmato time-sharing: con un solo processore, fa eseguire i processi a turno, in modo equo.
  • Ogni processo riceve un quanto di tempo; allo scadere viene sospeso (preemption) e la CPU passa a un altro.
Un processo smette di eseguire per due motivi
  1. Preemption: è scaduto il suo quanto di tempo (sospensione forzata).
  2. Sospensione volontaria: ha chiesto un servizio di sistema e deve aspettare (es. un'operazione di I/O).

4. Architettura a strati

5. Processi e thread in Linux

In Linux i thread sono realizzati come particolari processi, detti processi leggeri (lightweight process). Terminologia:

TermineSignificato
Processo leggeroprocesso creato per rappresentare un thread
Processo normaleprocesso che non è leggero
Processo / taskgenerico processo, normale o leggero (nel codice di Linux si dice task)

I processi leggeri dello stesso processo normale condividono tutta la memoria, esclusa la pila (come visto in L02).

6. Commutazione di contesto e scheduler

Contesto e context switch Il contesto di un processo è l'insieme delle informazioni su quel processo che il SO deve mantenere.
La commutazione di contesto (context switch) è la sostituzione del processo in esecuzione con un altro.

Come sopra, avviene per preemption (fine del quanto) o per attesa volontaria (es. aspettare un dato dall'esterno).

Lo scheduler è il componente del SO che decide quale processo mandare in esecuzione ed esegue il context switch. Obiettivi della politica di scheduling:

  • i processi più importanti (con priorità maggiore) vanno eseguiti prima;
  • i processi di pari importanza vanno trattati in modo equo: nessuno deve aspettare il proprio turno molto più degli altri.

7. Sistemi multi-processore (SMP)

L'architettura multi-processore meglio supportata è la SMP (Symmetric Multiprocessing):

  • due o più processori identici collegati a un'unica memoria centrale;
  • tutti accedono a tutte le periferiche;
  • un solo SO li controlla e li tratta tutti allo stesso modo.

Approccio di Linux: ogni task è assegnato a un processore (allocazione statica). I task vengono spostati solo se, in un controllo periodico, il carico risulta molto sbilanciato (load balancing).

Perché statico? Spostare un task su un'altra CPU significa perdere i dati nella sua cache: finché la cache della nuova CPU non si riempie, gli accessi in memoria sono più lenti.

Conseguenza utile per lo studio: Linux si può capire come se ci fosse un solo processore. Un processo è eseguito da una sola CPU e non "vede" le altre. Quando parliamo di processo corrente, in realtà ce n'è uno per ogni CPU; la funzione get_current() restituisce il processo corrente della CPU che la esegue.

8. Kernel non-preemptable

  • Il kernel di Linux (nella versione che studiamo) è non-preemptable: è vietata la preemption mentre un processo esegue codice del SO.
  • Questa regola semplifica molto la realizzazione del kernel (meno problemi di concorrenza al suo interno).
  • Compilando con l'opzione CONFIG_PREEMPT si ottiene un kernel preemptable, utile per sistemi real-time. Noi consideriamo solo la versione non-preemptable.

9. Protezione dei processi e gestione delle periferiche

Protezione

Il SO deve impedire che un processo danneggi il sistema o altri processi, quindi deve limitare le azioni che un processo può fare. Per riuscirci servono meccanismi hardware di protezione (es. modo utente / modo kernel).

Adattarsi all'evoluzione delle periferiche

Il SO deve seguire l'evoluzione dell'hardware, soprattutto delle periferiche. Linux lo fa così:

  • Periferiche viste come file: il programma non conosce i dettagli fisici. Es.: un programma stampa scrivendo sul file speciale associato alla stampante; se cambio stampante il programma non cambia, cambia solo il driver.
  • Deve essere facile aggiungere il software di gestione di una nuova periferica (device driver).
  • Deve essere possibile configurare il sistema solo con i driver che servono, altrimenti il SO diventerebbe enorme.

10. Kernel module

Kernel module Modulo che si può inserire nel sistema senza ricompilare l'intero kernel. Una volta caricato diventa parte integrante del SO: può accedere alle funzioni e alle strutture dati del sistema.
  • Si caricano dinamicamente, durante l'esecuzione, solo quando servono.
  • Sono così importanti che lo spazio di indirizzamento riservato ai moduli è doppio rispetto a quello del SO base.
  • Ciclo di vita: compila e collega (make) → carica (insmod) → … → rimuovi (rmmod).

Esempio: axo_hello

#include <linux/init.h>
#include <linux/module.h>

/* funzione di inizializzazione: eseguita quando il modulo viene caricato */
static int __init axo_init(void) {
   /* printk sostituisce printf, che nel kernel non è disponibile */
   printk("Inserito modulo AxoHello\n");
   return 0;
}
module_init(axo_init);   /* dice al sistema quale funzione eseguire al caricamento */

/* funzione di uscita: eseguita quando il modulo viene rimosso */
static void __exit axo_exit(void) {
   printk("Rimosso modulo AxoHello\n");
}
module_exit(axo_exit);

Compilazione ed esecuzione

# compila e collega (il makefile è complesso perché deve collegare le funzioni del SO)
# produce axo_hello.ko (ko = kernel object): l'equivalente di un eseguibile per il SO
make

# carica il modulo (sudo: servono i diritti di amministratore)
sudo insmod ./axo_hello.ko

# rimuovi il modulo
sudo rmmod axo_hello

I messaggi di printk finiscono nel log di sistema (si leggono ad esempio con dmesg).

11. Modello semplificato e dipendenza dall'hardware

Linux "semplificato"

Linux è troppo grande per essere descritto per intero, quindi nel corso si usa un modello semplificato che ne rispecchia fedelmente il funzionamento ma toglie dettagli e funzioni secondarie.

  • Si usano funzioni astratte: funzioni, strutture dati o costanti che sostituiscono gruppi di funzioni reali del codice sorgente.
  • Si riconoscono perché hanno nomi in italiano. Es.: lo stato ATTESA sostituisce i reali INTERRUPTIBLE e UNINTERRUPTIBLE.

Dipendenza dall'architettura hardware

  • Linux è scritto in C e compilato con gcc → è portabile su tutte le piattaforme che hanno gcc.
  • Alcune funzioni dipendono dall'hardware e sono scritte diversamente per ogni architettura (spesso con codice assembler); al link si sceglie l'implementazione giusta (makefile complessi).
  • Il codice dipendente dall'architettura si trova in linux/arch/; per x86 in linux/arch/x86/.

Architettura x64

  • Nel corso si fa riferimento all'architettura x86-64 in Long 64-bit mode, chiamata per brevità x64.
  • ISA definita nel 2000, evoluzione dell'x86 a 32 bit e compatibile con le versioni precedenti.
  • Può funzionare in 5 modi: Long 64-bit, Long Compatibility, Legacy Protected, Legacy Virtual 8086, Legacy Real.
  • È l'architettura dominante per PC, server e supercomputer.

12. Strutture dati per la gestione dei processi

Il contesto di ogni processo è salvato in strutture dati del SO. Per il processo in esecuzione, una parte del contesto, il contesto hardware, sta nei registri della CPU: quando il processo smette di eseguire va salvata in memoria, per poterla ripristinare quando tornerà in esecuzione.

Per ogni processo esistono (uno per processo):

  • il descrittore del processo (process descriptor): il suo indirizzo identifica il processo in modo univoco;
  • la pila di sistema (sPila) del processo.

Il descrittore: task_struct

  • Definito in <linux/sched.h>.
  • Allocato dinamicamente nella memoria del kernel ogni volta che si crea un processo.
  • get_current() restituisce il puntatore al task_struct del task in esecuzione.
  • Negli esempi, "i processi P e Q" significa due variabili struct task_struct *P, *Q; e P->pid è il campo pid del descrittore di P.
struct task_struct {
   pid_t pid;
   pid_t tgid;
   volatile long state;           /* -1 non eseguibile, 0 eseguibile, >0 fermato */
   void *stack;                   /* puntatore alla sPila del task */
   struct thread_struct thread;    /* contesto HW salvato */
   /* variabili per lo scheduling */
   struct mm_struct *mm;           /* gestione della memoria */
   /* variabili per lo stato di terminazione */
   struct fs_struct *fs;           /* informazioni sul filesystem */
   struct files_struct *files;     /* file aperti */
   ...
};

Nota il collegamento con la Lezione 2: pid e tgid sono proprio i campi da cui gettid() e getpid() prendono i valori.

Il contesto hardware: thread_struct

Dipende dall'hardware (per x86 è in arch/x86/include/asm/processor.h). Ci interessano tre campi che puntano alle pile:

CampoSignificato
sp0base della pila di sistema del processo
spposizione corrente nella pila di sistema
userspposizione corrente nella pila di modo utente

Leggere il descrittore da un kernel module

static void task_explore(void) {
   struct task_struct *ts;
   struct thread_struct threadstruct;
   int pid, tgid;
   unsigned long vsp, vsp0, vstack, usp;

   ts = get_current();                   /* task corrente */
   pid = ts->pid;  tgid = ts->tgid;
   printk("PID = %d, TGID = %d\n", pid, tgid);

   threadstruct = ts->thread;            /* informazioni sulle pile */
   vsp  = threadstruct.sp;
   vsp0 = threadstruct.sp0;
   vstack = (unsigned long) ts->stack;
   usp  = threadstruct.usersp;
   /* printk di ciascun valore */
}

Output (dal log di sistema):

[27663.251212] Inserito modulo Axo_Task
[27663.251214] PID = 7424, TGID = 7424
[27663.251215] thread.sp  = 0xFFFF 8800 5C64 5D68
[27663.251216] thread.sp0 = 0xFFFF 8800 5C64 6000
[27663.251217] ts->stack  = 0xFFFF 8800 5C64 4000
[27663.251218] usersp     = 0x0000 7FFF 6DA9 8C78
[27663.260995] Rimosso modulo Axo_Task
  • I messaggi hanno la numerazione del log di sistema perché a stampare è il SO.
  • PID = TGID → il processo ha un solo thread.
  • PID e TGID si potrebbero ottenere anche da un normale programma (getpid…), ma gli indirizzi della pila di sistema no: sono visibili solo dal kernel.
  • Gli indirizzi 0xFFFF… sono nello spazio del kernel; usersp (0x0000 7FFF…) è nello spazio utente.
  • La sPila va da stack (…4000) a sp0 (…6000): 8 KB (0x2000); sp sta in mezzo perché la pila cresce verso il basso a partire da sp0.

Riassunto

  • Linux domina server e mobile (Android); oltre metà del codice sono driver.
  • Il SO crea l'ambiente di esecuzione: processi sequenziali, paralleli, isolati; risorse condivise gestite centralmente tramite servizi.
  • Time-sharing: quanto di tempo; un processo si ferma per preemption o per attesa volontaria.
  • Struttura a strati: modo utente → chiamate di sistema → kernel (processi, memoria, driver, file system) → hardware.
  • Thread = processi leggeri; "task" = processo generico.
  • Scheduler: sceglie chi esegue (priorità + equità) e fa il context switch.
  • SMP: task assegnati staticamente alle CPU (cache), load balancing periodico; get_current() per CPU.
  • Kernel non-preemptable (salvo CONFIG_PREEMPT).
  • Kernel module: make → insmod → rmmod; printk invece di printf.
  • Ogni processo ha un task_struct (pid, tgid, state, stack, thread, mm, files…) e una sPila; il contesto HW è in thread_struct (sp0, sp, usersp).
